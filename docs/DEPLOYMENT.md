# Эволюция размещения

Путь: **ноутбук (H2)** → **тот же ноутбук (Compose + Postgres)** → **один VPS (тот же Compose)** → **ужесточение** (бэкапы, HTTPS, секреты). Оркестратор — не цель, а реакция на рост.

## 1. Только процесс Java

```bash
./mvnw spring-boot:run
```

Профиль `local`. Потеряли `data/` — потеряли журнал. Для разработки ок, для учёта денег — нет.

## 2. Docker Compose на своей машине

```bash
docker compose up --build
```

- API не знает, что он «в контейнере», кроме hostname БД
- Postgres недоступен снаружи как единственный способ работы приложения (порт 54332 — только отладка)
- обновление: пересобрать образ `api`, volume `ledger_pg` не трогать

Проверка с хоста:

```bash
curl http://127.0.0.1:48121/actuator/health
```

## 3. Тот же Compose на VPS

Минимальный канон:

1. JDK на сервере не нужен — только Docker.
2. Скопировать репозиторий или деплоить образ из registry (позже).
3. Файл `.env` с `DB_PASSWORD` и будущим `LEDGER_API_TOKEN` — права 600, не в git.
4. Перед API поставить Caddy: `https://ledger.example.com` → `:48121`.
5. Открыть в firewall только 80/443, не 5432.

Профиль `prod`: `DATABASE_URL`, `DB_USER`, `DB_PASSWORD`.

Схема `prod` уже описана в `application.yml`. Секреты в репозиторий не кладём.

## 4. Данные

Пока один диск VPS:

```bash
docker compose exec postgres pg_dump -U ledger ledger > backup-$(date +%F).sql
```

Хранить копии вне этой машины (второй диск, объектное хранилище). Volume Docker — не бэкап.

## 5. Когда менять форму

| Симптом | Следующий шаг |
| --- | --- |
| Нужен доступ с телефона | HTTPS + auth, этап 4 roadmap |
| Боитесь потерять журнал | `pg_dump` + проверка restore |
| Два сервиса (API и UI) | тот же compose, второй контейнер `web` |
| Нужен нулевой даунтайм | тогда уже не этот документ: отдельный ADR |

Kubernetes, managed Postgres, отдельный VPC — после того, как Compose на одной VM станет скучным, а не «как у больших».
